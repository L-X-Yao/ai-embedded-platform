## Why this library

- **Zero dependencies** -- no OS, no heap, no libc beyond `<stdint.h>`. Every component is a pure C99 static library.
- **No platform code inside** -- hardware access is injected through function pointers, never `#ifdef` per vendor. Every component cross-compiles for Cortex-M4 in CI; five have run on a GD32F405 board, the rest have only been exercised on the host (see [Verification status](#verification-status)).
- **Host-testable** -- every component compiles and runs on your desktop with `gcc` and `cmake`. No dev board needed to start integrating.
- **Verified, not just generated** -- every component passes the same gates (tests, audit, coverage, sanitizers, ARM build) and the gaps that remain are written down, not hidden.

## Quick start

Each component is a `.h` + `.c` pair in a self-contained folder. To use one:

```bash
# 1. Copy the component files into your source tree
cp wheels/drivers/bmp280/bmp280.{c,h} your_project/lib/bmp280/

# 2. Add two lines to your CMakeLists.txt
target_include_directories(your_app PRIVATE lib/bmp280)
target_sources(your_app PRIVATE lib/bmp280/bmp280.c)
```

Also copy `tooling/harness/contract.h` (a single header with optional runtime assertions). Then include the component header, inject your HAL callbacks, and call the API:

```c
#include "bmp280.h"

/* Provide your platform's I2C implementation */
static bool my_write_reg(void *ctx, uint8_t addr, uint8_t reg, uint8_t val) {
    return hal_i2c_write(addr, reg, &val, 1);  /* your HAL here */
}
static bool my_read_regs(void *ctx, uint8_t addr, uint8_t reg,
                         uint8_t *buf, uint16_t len) {
    return hal_i2c_read(addr, reg, buf, len);
}

static const bmp280_i2c_t i2c = {
    .write_reg = my_write_reg,
    .read_regs = my_read_regs,
    .delay_ms  = NULL,  /* optional */
    .ctx       = NULL,
};

static const bmp280_cfg_t cfg = {
    .addr   = BMP280_ADDR_LOW,
    .osrs_t = BMP280_OVERSAMPLING_2,
    .osrs_p = BMP280_OVERSAMPLING_16,
};

void app_main(void) {
    bmp280_t sensor;
    bmp280_data_t data;

    if (bmp280_init(&sensor, &i2c, &cfg) != BMP280_OK) {
        /* handle error */
    }

    if (bmp280_read(&sensor, &data) == BMP280_OK) {
        printf("%.1f C, %.0f Pa\n", data.temperature_c, data.pressure_pa);
    }
}
```

Every component follows this same pattern: inject HAL via a struct of function pointers, call `_init`, then use the API.

## Architecture: HAL injection

Components never call hardware directly. Instead, you inject platform-specific functions at initialization:

```
 +-----------+     function pointers     +------------------+
 | Component | <------------------------ | Your HAL / RTOS  |
 | (pure C)  |  write_reg, read_regs,   | (STM32 HAL, ESP  |
 |           |  delay_ms, gpio_write... |  IDF, bare metal) |
 +-----------+                           +------------------+
       |
       | same component binary
       v
 +-----------+
 | Host test |  mock functions injected
 | (desktop) |  for simulation testing
 +-----------+
```

This means:

- Components have zero compile-time platform dependencies
- The same source compiles for ARM Cortex-M, RISC-V, Xtensa, or x86 desktop
- Tests run on your development machine with mock HAL implementations
- No `#ifdef STM32` / `#ifdef ESP32` inside component code

### Known limits

Read these before putting a driver on silicon.

- **Only the five components above have run on real hardware.** Every other driver was exercised against a mock register model. Many of those models were written with the driver and repeat its mistakes, so a green test does not show that a register value is right. The bug surfaces on the board.
- **The datasheet review found real defects, and the rate is high.** Roughly 16% of the reviewed common-chip drivers (BMP280, MPU6050, SHT30 class) and 3 of 5 obscure-chip drivers had a wrong register offset, a missing bit mask or a missing sign extension. A stricter review in November 2026 covered 82 drivers and confirmed about 380 faults. About 230 are in the code of 65 drivers, from wrong product IDs to radios that were never calibrated, and about 155 are in test models, which accounts for 12 more drivers with a fault only in their model. It also found more in drivers the earlier review had passed. Driver faults that need no HAL change or large rewrite are fixed, but those fixes have not run on hardware either. Model faults are fixed only where a driver fix needed them. `bmi270`, `vl53l1x` and `vl53l0x` are marked not usable, `icm42688` could not be checked, and 21 drivers have had only the earlier review. Treat an unreviewed driver as a draft. See [docs/known-issues.md](docs/known-issues.md). Drivers that were not sampled should be assumed to carry a similar rate until you verify them; the review procedure is task type 14 in [docs/ai-workflow.md](docs/ai-workflow.md).
- **No RTOS and no MCU HAL ship here.** You supply the bus callbacks. A VSF HAL port for GD32F4xx lives in `vsf-addon/` as a worked example, and `vsf/` is an unmodified upstream snapshot kept for that port.
- **Licensing.** Components are MIT. The vendored FlashDB under `wheels/primitives/kvs/vendor/` and the VSF snapshot under `vsf/` are Apache-2.0 and keep their own notices.

## How it was built

- **Timeline.** 2026-04-21 to 2026-05-20: about 1,170 commits by one embedded engineer directing Claude Code, often several agents in parallel git worktrees.
- **Division of labour.** The human owns requirements, API approval, architecture decisions ([12 ADRs](docs/adr/README.md)), audits and hardware tests. The AI implements, writes tests, documents and runs the tooling.
- **The contract.** [CLAUDE.md](CLAUDE.md) (Chinese) is the standing instruction set the agent works under. [docs/wheel-contract.md](docs/wheel-contract.md) defines what a component must be, [docs/api-conventions.md](docs/api-conventions.md) fixes naming and error handling, [docs/ai-workflow.md](docs/ai-workflow.md) is the playbook for 14 task types, and [docs/debugging-playbook.md](docs/debugging-playbook.md) is the running list of mistakes so they are not repeated.
- **Why the tooling exists.** Generation was fast (about 15 minutes from scaffold to green tests for a typical driver) and the defect rates above are what fast looks like without checks. Everything under `tooling/` was built in response to a class of bug that had already slipped through once.
- **Not included.** This is the public copy of an internal monorepo. The `projects/` directory (customer firmware that consumed these components) is not published; the places in the docs that mention `projects/flybox` or `projects/drone_light` refer to it.

## See it in action

Build and run the MQTT telemetry demo on your desktop, no hardware needed:

```bash
cd examples/mqtt_telemetry_demo
cmake -S . -B build && cmake --build build && ./build/mqtt_telemetry_demo
```

It drives a mocked BMP280 through `sensor_hub`, encodes with `mqtt_packet` and walks the `mqtt_client` state machine through connect, publish, PUBACK and reconnect.

### Flagship examples

Five runnable integration examples that cover the most common embedded use cases. Each compiles and runs on your desktop with zero hardware:

```bash
cd examples/<name>
cmake -S . -B build && cmake --build build && ./build/<name>
```

| Example | Wheels used | What it demonstrates |
|---------|------------|---------------------|
| **mqtt_telemetry_demo** | bmp280, sensor_hub, mqtt_packet, mqtt_client | IoT sensor → MQTT publish pipeline with state machine |
| **industrial_monitor** | pid_controller, rate_limiter, fixed_point, ina219, ads1115, canbus, telemetry, task_watchdog | PID control loop + CAN bus + power monitoring + watchdog |
| **gps_tracker** | kalman_1d, base64, uuid, ds3231, sd_spi, sntp_client, ubx_parser | GPS parsing → Kalman filtering → SD card logging → NTP sync |
| **display_hub** | sh1106, hd44780, tm1637, max7219, lcd_st7789, ili9341 | 6 display types (OLED, LCD, 7-seg, LED matrix, TFT) via mock HAL |
| **smart_home** | debounce, timer_wheel, led_pattern, bme280, bh1750, ws2812, cbor_lite, scheduler, event_bus | Event-driven IoT hub with sensor polling + CBOR encoding + LED effects |

All 27 examples in `examples/` compile on host. The five above produce the most informative output.

## Running tests

```bash
# Prerequisites: gcc, cmake, ninja, python3, pytest

# Test everything (about one minute on a laptop)
make test-parallel

# Test a single component
bash tooling/test/test_all.sh wheels/drivers/bmp280

# Run the 63-check audit
python3 tooling/audit/audit_wheels.py --quiet

# Coverage for one component
bash tooling/test/coverage_wheel.sh wheels/drivers/bmp280
```

## Project structure

```
ai-embedded-platform/
├── wheels/
│   ├── primitives/       L0: pure software (CRC, buffers, math, crypto)
│   ├── drivers/          L1: sensor/peripheral drivers (I2C, SPI, GPIO)
│   ├── protocols/        L2: protocol parsers (MQTT, Modbus, HTTP)
│   └── modules/          L3: higher-level modules (CLI, OTA, logging)
├── examples/             Integration examples combining multiple components
├── tooling/
│   ├── harness/          Test framework headers
│   ├── codegen/          Test code generators
│   ├── test/             Test runners (coverage, fuzz, mutation)
│   ├── audit/            Automated compliance checker
│   ├── wheel/            Scaffold, promote and gate scripts
│   └── session/          Multi-agent dispatch and session bootstrap
├── docs/
│   ├── wheel-contract.md Component specification
│   ├── api-conventions.md  Naming and error handling conventions
│   ├── ai-workflow.md    Task playbook for the AI agent
│   ├── known-issues.md   Every defect found by audits and reviews
│   └── adr/              Architecture decision records
├── vsf-addon/            GD32F4xx HAL port for the VSF framework (example consumer)
├── vsf/                  Unmodified upstream VSF snapshot (Apache-2.0)
└── templates/            Starter templates for new projects
```

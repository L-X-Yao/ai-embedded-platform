# 平台哲学：人 10% + AI 90%

## 背景

用户是嵌入式软硬件工程师，长期做各种项目（MCU / BLE / WIFI / USB / FS / GUI 等）。每个新项目从零搭脚手架+写驱动+调协议栈，消耗时间大部分是重复劳动。

**这个平台要改变这个分工**：

| 人的时间（10%） | AI 的时间（90%） |
|----------------|-----------------|
| 提需求、定功能边界 | 按需求写应用逻辑 |
| 硬件选型、原理图评审 | 调用已有轮子组装 |
| 架构决策（用什么轮子、怎么分层） | 调 pytest、修 bug、写测试 |
| 性能 / 实时性调优（涉及测量） | 生成配置、脚手架、模板代码 |
| 安全边界定义（可信数据域） | 重构、文档、接口适配 |
| 把关最终交付 | 迭代到测试全绿 |

## 达成路径

### 飞轮效应

```
项目 1：AI 踩坑 × 10，产出 2 个轮子（第一版，不够通用）
     ↓ 用户沉淀踩坑 → memory + debugging-playbook
项目 2：AI 踩坑 × 3，复用 1 个轮子，产出 3 个新轮子 + 1 个升级
     ↓ 轮子接口趋稳 → wheel-contract 被迭代
项目 3：AI 踩坑 × 1，复用 3 个轮子，产出 2 个轮子
     ↓ 模板化 → templates/ 里出现 "data-logger"、"ble-peripheral"
项目 5：AI 80% 时间在复用，用户 15% 在定需求和评审
项目 10：新项目起步 = 选 template + 配参数，3 天出原型
```

### 投资回报

前 2-3 个项目 **ROI 是负的**——加了 CLAUDE.md 维护、轮子文档、测试编写等开销，但没省多少时间。

从第 4 个项目起 ROI 开始为正，第 6-8 个项目起**显著为正**。

**不要在第一个项目就期待省时间。** 第一个项目的目标是"把规范跑通"。

## 硬约束（不可妥协的底线）

1. **所有轮子必须有测试**。没测试的代码不叫轮子，叫黑盒。
2. **测试必须在 sim 里能跑**（VSF linux host / QEMU / native）。不能只依赖硬件的轮子要单独标记 `HIL-ONLY`。
3. **轮子的 API 必须文档化**。AI 写完不写 README 等同没写。
4. **踩坑必须文档化**。AI 自己解决的 bug 也要更新 `debugging-playbook.md`——否则下个 session 的 AI 会重踩。
5. **不动用户的项目源码**（除非明确任务范围包含）。

## 人 / AI 分工清单

### 只有人能做的

- 硬件选型
- 原理图 review
- 测量类工作（示波器、逻辑分析仪、万用表）
- 最终产品交付前的 sign-off
- 跨项目的架构演进决策（什么时候该把 A 拆成 B+C）
- 跟客户谈需求
- 判断"AI 写的这块代码可不可信"（code review 终审）

### AI 可以做、且应该做的

- 按轮子/模板生成项目脚手架
- 写驱动代码（参考现有 pattern）
- 写协议栈适配层
- 写测试（单元 + 集成）
- 调 build system（cmake / Kconfig）
- 写 / 改文档
- 定位常见 bug（编译错、链接错、逻辑错）
- 从 pytest 错误驱动修改

### 灰色地带（AI 先做，人审）

- 新轮子的接口设计（AI 提案，人拍板）
- 性能优化（AI 实现，人测量验收）
- 安全相关（AI 按清单写，人复核）
- 跨平台移植（AI 按 HAL 抽象写，人在真机验证）

## 与 VSF 的契合

这个哲学和 VSF 的设计不谋而合：

- VSF 的"皮肤"让应用层代码与底层解耦 → 轮子可跨 MCU 复用
- VSF 的 PLOOC OOP 让接口清晰 → AI 按"class"生成代码模式统一
- VSF 的统一 HAL 让驱动可替换 → 轮子能跑在真机和 sim
- VSF 的小资源特性让 sim 到真机的切换代价低

但 VSF 本身**不提供这个工作流**——这个工作流是我们在 VSF 之上构建的。

# 平台哲学：人做决策，AI 做执行

## 背景

用户是嵌入式软硬件工程师，长期做各种项目（MCU / BLE / WIFI / USB / FS / GUI 等）。每个新项目从零搭脚手架+写驱动+调协议栈，消耗时间大部分是重复劳动。

**这个平台要改变这个分工**：

| 人的职责（决策） | AI 的职责（执行） |
|----------------|-----------------|
| 提需求、定功能边界 | 按需求写应用逻辑 |
| 硬件选型、原理图评审 | 调用已有轮子组装 |
| 架构决策（用什么轮子、怎么分层） | 调 pytest、修 bug、写测试 |
| 性能 / 实时性调优（涉及测量） | 生成配置、脚手架、模板代码 |
| 安全边界定义（可信数据域） | 重构、文档、接口适配 |
| 把关最终交付 | 迭代到测试全绿 |

## 达成路径

### 飞轮效应（定性示意，不是承诺）

下面的数字是**机制示意**，不是指标承诺——实际节奏依团队 / 项目复杂度 / AI 能力演进而定：

```
项目 1：AI 踩坑多，产出少量轮子（第一版，可能不通用）
     ↓ 沉淀踩坑 → memory + debugging-playbook
项目 2：AI 踩坑减少，开始复用，产出新轮子 + 升级旧的
     ↓ 轮子接口趋稳 → wheel-contract 被迭代
项目 3：AI 踩坑显著少，复用率上升
     ↓ 模板化 → templates/ 出现成熟起点
项目 N（N 足够大）：新项目起步 = 选 template + 配参数 + 写应用特殊逻辑
```

### 投资回报（方向，非具体承诺）

**前几个项目 ROI 预计为负**——文档/测试/规范的前置开销压倒省下的 AI 开发时间。

**量化投入产出的节奏**：每 3 个月做一次诚实 ROI 评估（同类任务工时降低百分比 / wheel 复用率 / 踩坑频率）。如果连续两次评估看不到改善趋势，**停下来想哪个假设错了**。

**不要在第一个项目就期待省时间。** 第一个项目的目标是"把规范跑通 + 产出可复用的第一批轮子"。

## 硬约束（不可妥协的底线）

1. **所有轮子必须有测试**。没测试的代码不叫轮子，叫黑盒。
2. **测试必须在 sim 里能跑**（VSF linux host / QEMU / native）。不能只依赖硬件的轮子要单独标记 `HIL-ONLY`。
3. **轮子的 API 必须文档化**。AI 写完不写 README 等同没写。
4. **踩坑必须文档化**。AI 自己解决的 bug 也要更新 `debugging-playbook.md`——否则下个 session 的 AI 会重踩。
5. **不动用户的项目源码**（除非明确任务范围包含）。

## 人 / AI 分工清单

### 只有人能做的

- 硬件选型
- 原理图 review
- 测量类工作（示波器、逻辑分析仪、万用表）
- 最终产品交付前的 sign-off
- 跨项目的架构演进决策（什么时候该把 A 拆成 B+C）
- 跟客户谈需求
- 判断"AI 写的这块代码可不可信"（code review 终审）

### AI 可以做、且应该做的

- 按轮子/模板生成项目脚手架
- 写驱动代码（参考现有 pattern）
- 写协议栈适配层
- 写测试（单元 + 集成）
- 调 build system（cmake / Kconfig）
- 写 / 改文档
- 定位常见 bug（编译错、链接错、逻辑错）
- 从 pytest 错误驱动修改

### 灰色地带（AI 先做，人审）

- 新轮子的接口设计（AI 提案，人拍板）
- 性能优化（AI 实现，人测量验收）
- 安全相关（AI 按清单写，人复核）
- 跨平台移植（AI 按 HAL 抽象写，人在真机验证）

## 技术架构

Wheel 是零 OS 依赖的被动库（纯 C99 + 函数指针注入），设计为 AI 原生：

- **统一模式**：所有 wheel 遵循相同的 scaffold 模板 + API 约定 → AI 学一次，全部适用
- **Host 可测**：`gcc + cmake` 秒级验证 → AI 开发循环极快
- **零依赖**：不绑定任何 RTOS/芯片 → 每个 wheel 是通用资产，跨项目零成本复用
- **被动库**：wheel 不创建任务/不加锁/不 sleep → 应用层控制一切，AI 生成胶水代码

完整架构见 `docs/architecture.md`。

## 与 VSF 的关系

VSF 是项目级基座（ADR-007），不是 wheel 的依赖：

- VSF 为项目提供 RTOS 调度、HAL、USB/BLE 等能力
- Wheel 不知道 VSF 的存在——通过 HAL 回调获得硬件能力
- 如果项目换其他 RTOS（FreeRTOS / RT-Thread / 裸机），wheel 零改动

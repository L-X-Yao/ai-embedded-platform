# ADR 011: Wheel 构建策略从需求驱动转为生态驱动

**状态**：accepted
**日期**：2026-05-01
**决策人**：@L-X-Yao

## 背景

原策略（ADR-006 + WISHLIST.md）要求：新 wheel 必须先 grep VSF 原生，且必须有真实项目触发（信号次数 ≥ 1）才能开工。

两个前提已经变化：
1. Wheel 设计为零 OS 依赖（纯 C99 + HAL 注入）——即使 VSF 有同功能的组件，VSF 的版本绑定 VSF 内核，我们的版本全平台通用。"VSF 有就不做"逻辑不再成立。
2. AI 开发成本趋近于零——等待项目触发是人为瓶颈，不是资源约束。

## 考虑过的选项

- **选项 A：保持需求驱动**。继续等项目触发。
  - 优点：不做无用功
  - 缺点：生态积累速度受限于项目节奏

- **选项 B：生态驱动，主动构建**。按"嵌入式常用"标准选择 wheel，不等项目触发。
  - 优点：快速积累生态，AI 飞轮转得更快
  - 缺点：可能构建低使用率的 wheel（但 AI 成本近零，风险可接受）

## 决策

选择 B。主动按领域覆盖度构建 wheel，不等项目触发。

### 规则变化

| 规则 | 旧 | 新 |
|------|-----|-----|
| grep VSF | 门禁（有就不做） | 参考（可借鉴设计，不阻断） |
| WISHLIST 信号次数 | ≥ 1 才做 | 不需要信号 |
| 选型标准 | "哪个项目需要" | "嵌入式常用吗" |
| ADR-010 查开源 | 仍然有效 | 仍然有效（查通用开源库，不限于 VSF） |

### 不变的规则

- Wheel 是被动库（见 `docs/architecture.md`）
- 需要创建任务/中断/OS 调用的功能不做成 wheel
- 质量标准不降（scaffold + test + audit）
- ADR-010（优先采纳开源实现）仍然有效

## 后果

- 好：wheel 生态增长不再受限于项目节奏
- 好：组件库更快达到有竞争力的规模
- 坏：可能构建一些长期无项目使用的 wheel（代价小——AI 成本近零，每个 wheel ~200 LOC）
- 坏：ADR-006 的"grep VSF"铁律降级，失去一道防重复的关卡（但 wheel 独立于 OS 后这道关卡本身已失去意义）

## 何时应重新评估

- wheel 总量超过 150 个且发现 >30% 从未被任何项目使用 → 考虑收紧选型标准
- AI 开发成本显著上升 → 恢复需求驱动
